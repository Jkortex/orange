# 第 1 章 开启奇妙冒险

### 本章核心内容

- 探究究竟是什么让某些数据结构与算法如此“奇妙”
- 定义数据结构、算法以及渐进复杂度
- 实现并反转一个不可变单链表

---

**算法**（algorithm）是解决特定问题的具体步骤；**数据结构**（data structure）则是组织和存储数据的方式。利用组织良好的数据来求解现实问题，构成了计算机编程的全部核心。但是，究竟是什么让某些数据结构与算法显得如此“奇妙”（fabulous）？对我而言，它通常源自以下几个维度的交织融合：

- **解决实际工程问题，却走出非寻常之路**：本书中介绍的绝大多数算法与数据结构，都是我在没有现成库函数支持的情况下，为了解决现实工程问题而深入摸索习得的。例如，为了解决“在所有代码修改历史中，存在哪些通用的编辑模式？”这一问题，我深入研究了反合一（Anti-unification）算法。通常，这些新概念是我通过阅读前沿学术论文才掌握的，因为在大学书架上的常规本科教材里根本找不到它们。
- **达成反直觉的奇妙效果**：在应用程序中管理状态变更与实现撤销/重做（Undo/Redo）逻辑的最佳手段之一，竟然是将状态存储在**完全不可变更**的数据结构中，这听起来多少有些违背直觉。默认拥抱不可变数据结构，彻底改变了我用代码思考和解决问题的方式；与此同时，它也让我的代码更加健壮、缺陷更少且更容易推演。本书的第一部分将深入探讨不可变数据结构。
- **跨越诸多领域通用同一解法**：使用**回溯**（即深度优先搜索）在树中查找元素并不令人意外；但当你发现类似的回溯搜索既可以用来为地图上的国家涂色，又能用来求解数独谜题时，多少会感到惊奇；而当你进一步发现它也是代码编辑器中自动化源码美化排版算法的基础时，就只能赞叹其奇妙了。目睹这些看似不相关的领域之间的深层联系，促使我将特定问题视为更通用可解问题的特例，从而重塑了我的解题思维方式。我们将在第二部分探讨此类算法。
- **强调业务意图，而非底层机制**：大量日常代码表面上看其目的无非是在更新一堆变量、运行循环、捕获异常等等，但这绝非代码的真正目的——那些操作仅仅是代码达成业务目标的执行机制。如果代码行文直接运用其所要解决的问题领域中的核心概念，那么代码将远比以往更易阅读、编写、维护和推演。本书的最后一部分将重点探讨如何不仅实现概率相关问题的算法，而且让代码在更高的抽象层次上表达。
- **如同惊艳的魔术手法**：Hughes 链表是一种实现了单链表全部特性的二叉树数据结构，但在初看之下，它似乎完全不包含任何数据！这究竟是如何做到的？揭开幕后的魔术机关，将向你揭示编译器如何自动为你生成隐藏的数据结构。
- **淋漓尽致地发挥编程语言特性**：像 C# 这样的现代编程语言所具备的表面特性极为庞大，在大多数时候，我们仅仅使用了其冰山一角的威力。直到我用 Finger Tree（手指树）实现了一个不可变双端队列（Deque），并亲眼见证它如何通过递归泛型类型强制执行编译期类型安全（这在基于模板展开的语言中根本无法做到），我才真正理解了 C# 泛型与 C++ 模板之间的本质区别。
- **跳出既有框架，颠覆问题本质**：有时我们习惯于死抠细节以挤出边际性能提升，但更应该退后一大步，思考是否存在一种完全不同的问题求解路径。对我而言最典型的例子就是 Bill Gosper 用于运行元胞自动机的 HashLife 算法。通过将点阵网格重新抽象为不可变四叉树而非传统的可变数组，该算法实现了看似不可能的指数级时空性能飞跃。
- **与数学理论的深刻联结**：你无需理解恒星天体物理学就能制造望远镜，同样，你无需理解范畴论也能编写计算机程序。然而，探寻函数、可空值类型、任务（Task）、序列以及随机数生成器等截然不同的数据类型之间所共享的底层代数模式，既令人着迷，又极具启迪意义。
- **体会创造的纯粹乐趣！**：编程本质上是一种创造性艺术。你在脑海中构建出机器应当如何解决问题的构想，敲下对这一解法的精确描述，片刻之后，原本抽象的思想便化为了现实中切实运转的解题机器。从我 9 岁在小学图书馆的 Commodore PET 上编写代码开始，这种乐趣便伴随着我；亲手创造出能够正常工作的成果所带来的满足感，从未消退。实现本书中的这些算法与数据结构，是我职业生涯中最开心的时光。

市面上有许多优秀的著作讲解大学计算机专业的基础必修知识：如何平衡红黑树、如何排序数组、如何构建优先队列等等。我们将从栈和队列等基础知识出发，但会迅速跨越它们，直奔那些在学校很少讲授、通用类库中难觅踪迹，却在实际开发中大放异彩的奇妙算法与数据结构。在我的职业生涯中，我必须持续向工具箱中增添全新利器；我希望本书也能为你做到这一点。而我更宏大的目标，是带你重温那种着迷、欣喜与探索的乐趣，并在此过程中重塑你对编程的认知。

## 1.1 定义数据结构、算法与复杂度

首先我们简要界定几个核心概念：

- **数据结构**（data structure）：顾名思义，是以一种有组织、结构化的方式存储信息的方法。在 C# 中，我们将按惯例使用数组、类（class）、结构体（struct）、记录（record）和接口（interface）来构建数据结构。
- **算法**（algorithm）：是执行时能够解决特定问题的一组有限步骤序列。算法不一定是确定性的，许多算法都包含“选取随机数”的步骤。算法也不一定非要在计算机上执行，且即使执行的步数庞大，概念上也并不必然复杂。“估算如果该用户浏览了这些广告中的每一条所产生的平均收益，然后向其展示期望收益最高的那条广告”，虽然包含了大量数学计算，但在逻辑上非常易懂。

> **术语渊源**  
> “算法”（Algorithm）一词源于 9 世纪波斯数学家阿尔·花拉子米（Al-Khwarizmi）的名字，他的著作同样为我们带来了“代数”（Algebra）这个词汇。

算法的**复杂度**（complexity）描述了算法所求解问题的**规模**（size）与求解该规模问题所需的**开销**（cost）之间的增长关系。这里的开销通常以时间、内存或我们关心的其他系统资源来衡量。描述规模与开销之间关系的工业标准是**大 O 记号**（Big O Notation），由德国数学家保罗·巴赫曼（Paul Bachmann）于 19 世纪末创立。按增长速率从小到大排列，常见的复杂度类别及其典型问题如下：

- $O(1)$ **常数阶**（constant）：无论问题规模增长到多大，开销始终保持恒定。求解“这个数组的第一个值是什么？”的开销，无论数组包含 10 个还是 10 亿个元素都完全相同。
- $O(\log n)$ **对数阶**（logarithmic）：当问题规模翻倍时，算法开销仅增加固定的常数步。如果我们有 $n$ 部电话，每部电话都需要唯一的号码，那么随着 $n$ 的增长，电话号码所需的位数与 $\log n$ 成正比。对数阶算法的开销增长极其缓慢，在工程实践中几乎永远不会成为现实程序的性能瓶颈。（对数的底数通常默认为 2，但在大 O 记号中选用任何大于 1 的常数底数渐进上都是等价的。）
- $O(n)$ **线性阶**（linear）：当问题规模翻倍时，算法开销也随之翻倍。如果我们要计算 $n$ 个 32 位整数的总和，求和的时间开销将随着 $n$ 的翻倍而翻倍。当问题规模扩大时，线性阶算法的性能开销开始能够被用户感知，但用户通常很容易接受“数据表规模扩大一倍，统计耗时也增加一倍”。
- $O(n \log n)$ **拟线性阶**（quasilinear）：开销增长快于线性阶，但远慢于平方阶。诸如“对包含 $n$ 个字符串的列表进行排序”通常采用拟线性阶算法完成。列表长度翻倍时，排序所需时间略微超过原来的两倍，但远未达到四倍。
- $O(n^2)$ **平方阶**（quadratic）：当问题规模翻倍时，算法开销会变为原来的四倍。“将 $n$ 个小字符串直接拼接在一起”的朴素算法在时间和内存上都是平方阶的。这类本身可以通过优化以更低成本完成的算法，常常被称为“意外的二次方”（accidentally quadratic）。在工程实践中，如果你希望系统能够线性横向扩展以支撑大规模数据，必须竭力避免平方阶及更差的算法。用户会明显感受到：数据规模仅增加了 10 倍，运行耗时却暴涨了 100 倍！
- $O(2^n)$ **指数阶**（exponential）与 $O(n!)$ **阶乘阶**（factorial）：开销增长极快，以至于除了极微小的输入规模之外，在计算上都是不切实际的。所有解法均为指数阶或更差的问题被称为**难解问题**（intractable）。例如“列出一副包含 $n$ 张扑克牌的所有可能洗牌顺序”，就是典型的难解问题。

![图 1.1 对数、线性、拟线性、平方与指数增长曲线对比](/media/posts/fabulous-algorithms/img-01738.jpeg)
*图 1.1：常见渐进增长曲线对比图。对数曲线最为平缓，增长极慢；而指数曲线最为陡峭，增长极其剧烈。*

衡量问题的规模通常非常直观。如果算法处理的是一个集合，我们通常采用集合中元素的个数。如果用于衡量问题规模的物理量不够直观，必须明确声明。例如，树上的某些算法在时间上与树的高度成线性关系，而非树中的节点总数，这一点必须阐述清楚。

开发者有时会陷入一个不良习惯：只从时间维度来思考开销。请务必牢记两点：首先，我们同样密切关注非时间维度的开销，例如内存占用与其他系统资源；其次，时间本身也存在多种衡量维度：最优情况时间、平均情况时间以及最坏情况时间都至关重要。我们在第 2 章中会看到，它们之间的差异可能非常微妙。在存在歧义的情况下，我会在给出算法复杂度时明确说明其指向的具体开销指标。

> **警告：渐进复杂度占优并不等于实际更优**  
> 具有更好渐进复杂度的算法，在实际工程中并不一定总是更好的选择。当我在 Visual Basic（VB）团队实习时，我注意到 VB 字符串搜索方法采用的朴素算法在最坏情况下是 $O(n^2)$。我当时在学校学过该问题存在线性复杂度的算法（如 KMP），便疑惑为何要采用一个“更差”的算法？该方法的原作者耐心地向我解释：**可扩展性只有在问题规模变大时才有意义**。VB 程序员并不会在数百万字符的长文本中搜索几千字符的长模式串；相反，他们绝大多数时候只是在短字符串中查找空格或逗号。尽管朴素算法的最坏情况很糟糕，但在典型的小输入上，它具有极高的 CPU 缓存命中率与近乎零的初始化常数开销，运行速度如闪电般迅速。

## 1.2 不可变单链表

作为一次热身练习，我们来实现一个不可变链表类，并编写反转该链表的方法（代码清单 1.1）。这个练习也是我们重温性能复杂度分析的绝佳机会。首先，给出数据结构的递归定义：**单链表（linked list）要么为空，要么由一个值（Value）紧随一个尾部链表（Tail）构成**。第 2 章将详细展开为什么不可变性如此重要且实用。

代码清单 1.1 示例不可变单链表：

```csharp
sealed record LinkedList<T>(T? Value, LinkedList<T>? Tail)
{
    // C# 编译器在此推断 LinkedList<T>
    public static LinkedList<T> Empty = new (default, null);
    
    // 向链表头部压入新元素
    public LinkedList<T> Push(T value) => new (value, this);
    
    // 判断是否为空链表
    public bool IsEmpty => this == Empty;

    // 存在性能隐患的 ToString 实现
    public override string ToString()
    {
        var s = "";
        for (var list = this; !list.IsEmpty; list = list.Tail!)
            s += list.Value + " ";
        return s;
    }
}
```

> **注意**  
> 如果你对 C# 的 `record` 记录类，或者用于标记可空性与非空断言的 `?` 和 `!` 语法不够熟悉，请参阅附录 A。

仅仅短短十几行代码，我已经做出了若干关键的设计决策。你能从中看出哪些值得商榷的地方吗？让我们逐一剖析其中的精妙与缺陷：

- `record` 类的参数在默认情况下是只读的，这使得记录类成为构建简洁不可变类型的利器。
- 在许多编程语言中，传统上习惯用 `null` 引用来表示空链表。但在面向对象语言中，这种设计会引发一系列问题；空链表本身应该是一个合法的对象实例，我们可以在其上直接调用方法。因此，我决定用一个 `Value` 与 `Tail` 均为 `null` 的特殊链表节点来表示空链表。然而这种选择依然容易出错：例如，调用方可能构造出一个非空但包含非法 `Tail` 的孤立节点；在理想设计中，应当从类型系统层面让非法状态无法表达。第 2 章中我们将展示一种更优雅的空链表建模方式。
- `Push` 和 `IsEmpty` 成员并非严格必需，但它们为该类型的使用者提供了直观友好的 API 语法。

### 1.2.1 迄今为止的性能表现

在实现链表反转之前，我们先评估一下当前实现的性能特征：

- 使用 `new` 或 `Push` 创建新的链表节点，在时间和额外内存开销上均为 $O(1)$。因此，创建一个包含 $n$ 个元素的链表在时间和空间上都是标准的 $O(n)$。
- 记录类型（record）会自动重写相等性比较运算符。因此我的 `IsEmpty` 属性在执行时，首先检查 `this` 与 `Empty` 是否引用相等；接着它会执行一段生成的代码，最终调用 `int` 的相等性运算符。如果我们正在检查的链表恰好以 0 开头，它会在最终比较 `this.Tail` 与 `Empty.Tail` 的引用之前执行更多的比较分支。这段代码逻辑并没有错，复杂度也是 $O(1)$，但相比直接判断 `IsEmpty => Tail == null`，其常数开销明显要高得多。
- 谈到这里，开发者经常忘记对编译器自动生成的代码进行性能分析，但这些代码确实存在并可被用户调用。记录类会自动免费获得编译器生成的 `IEquatable<T>` 实现和重载的 `==` 运算符。生成的代码在链表上执行的是**值相等性比较**，而不是**引用相等性比较**，这往往出乎意料，且代价远高于引用比较。
- 更严重的隐患在于：由于数据结构是递归定义的，编译器生成的相等性运算符同样也是递归调用的！在两个很长的链表上执行相等性比较可能会导致调用栈溢出（Stack Overflow）。如果我们确实需要链表的值相等性比较，应当提供非递归的显式实现。
- 你很可能已经注意到，`ToString` 的朴素实现陷入了字符串拼接的经典“意外二次方”陷阱（$O(n^2)$）。每次向累加器字符串追加内容时，之前的字符串都会被完整复制到新分配的字符串中，而旧字符串沦为垃圾回收器的负担。该实现在时间和额外内存分配上都是 $O(n^2)$ 的，应当重构成基于 `StringBuilder` 的 $O(n)$ 实现。

> **提示**  
> 哪怕是极其短小、看似微不足道的代码片段，背后也可能隐藏着严重的性能暗礁。

### 1.2.2 反转不可变单链表

在前言中我提到，在 1996 年微软的面试中，第一位面试官让我反转一个单链表。我当时给出的解法在本质上就等同于下面这个方法，你可以将其添加到代码清单 1.1 的类中：

```csharp
public LinkedList<T> Reverse()
{
    var result = Empty;
    for (var list = this; !list.IsEmpty; list = list.Tail!)
        result = result.Push(list.Value!);
    return result;
}
```

这段逻辑非常直截了当：创建一个空链表，依次遍历原始链表中的每个节点，将每个元素逐一压入新链表头部，从而构造出一个元素顺序完全相反的新不可变单链表。由于所有链表都是不可变的，原始链表在此过程中毫发无损。编写如下测试代码：

```csharp
var list = LinkedList<int>.Empty.Push(10).Push(20)
           .Push(30).Push(40).Push(50);
var list2 = list.Reverse();
Console.WriteLine(list);
Console.WriteLine(list2);
```

运行输出完全符合预期：

```text
50 40 30 20 10 
10 20 30 40 50 
```

`Reverse` 方法的性能特征同样一目了然：它在时间开销和额外内存分配上都是严格的 $O(n)$。

## 1.3 前方的挑战

在接下来的奇妙冒险中，我们将首先审视栈、队列和树等我们耳熟能详的传统数据结构，但每一种结构都会展现出令人惊艳的全新视角。我们将探索通过持久化（persistence）与记忆化（memoization）实现的时空压缩、重排列表的优雅算法，以及一种看似在常数时间内反转链表的奇特构造。

随后，我们将深入探索我在构建现代开发者工具时遇到的核心算法。我们将剖析用于图着色的回溯搜索算法及其在工具链中的惊人应用；揭示 IDE 如何自动化排版美化源代码；并探讨语法树的合一与反合一在代码静态分析与模式提取中的巨大威力。

旅程的终点将为必须面对概率、随机性与统计推断的开发者打造一套坚实的工具箱。贝叶斯推断在当今诸多业务场景中愈发关键，但传统计算机教材对此涉及甚少，且诸多语言开箱即用的随机数库根本无法胜任严谨的概率建模。当我在工作中必须快速掌握统计推断时，从零构建这一套轻量级工具库极大地帮助我理清了思路、把握了本质，写出了更加严谨可靠的代码。

在此过程中，我们还将插入几次简短的理论闲聊，涉足范畴论这一深奥数学工具与我们每天使用的通用数据类型之间的优美代数关联。

我们将统一采用 C# 作为实现语言，但本书中的几乎所有思想都可以无缝迁移到其他现代主流面向对象与函数式语言中。任何熟悉 C++、Java 或 Python 的开发者都能轻松看懂代码。

在第 2 章中，我们将更深入地考察不可变单链表，看看还能发掘出哪些妙用。我们将基于不可变链表构建更加复杂的数据结构，并探索一种颠覆传统性能分析直觉的链表实现方式。

## 本章小结

- 关于列表、树、哈希表等标准数据结构及其排序、搜索算法的书籍汗牛充栋，主流类库中也早已内置。本书聚焦于那些鲜为人知、非传统但在我的工程生涯中发挥过关键作用的奇妙数据结构与算法。我挑选了那些最引人入胜的主题：反直觉的、宛若魔术的，或是突破语言表达边界的结构。
- 书中的绝大多数主题，都是我在工程工作中遭遇硬骨头、急需向工具箱添置新武器时深入钻研掌握的。如果你在实际工作中也面临类似的难题，希望本书能省去你啃读晦涩学术论文的苦功。
- 对我而言更重要的是，这些奇妙的探险让我对程序员的创造力有了更深刻的敬意，它们重塑了我对编程这门手艺的思考。这一路充满了乐趣，希望你也能感同身受。
- 渐进复杂度衡量的是解法随输入问题规模扩大时的扩展表现。若要让系统具备良好的大规模扩展能力，通常需要算法性能优于平方阶。
- 复杂度分析充满微妙细节。必须牢记时间并非唯一的资源约束；在现实场景中，避免极端的最坏情况往往比追求极致的平均性能更为关键。
- 如果实际业务中的输入规模始终极小，渐进复杂度的影响便相对微弱，常数因子与缓存局部性更为关键。
- 拥有不可变链表之后，反转链表的操作极为纯粹直观。第 2 章我们将探索更多不可变集合结构。
