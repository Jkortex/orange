# 第 3 章：OpenTel 电商系统架构与领域建模

## 引言

在第 1 章中，我们看到了看似健康的大盘背后可能隐藏着一次静默的结账失败。本章将正式介绍这一故障真实上演的具体系统：**OpenTel E-Commerce（OpenTel 电商系统）**。

从第 2 章中，我们还提炼出了一个贯穿全书的核心认知：Rust 的运行时与内存行为深刻塑造了生产环境中的具体故障表象。在负载压力之下，内存分配压力、锁争用以及异步任务调度，都会跨越服务边界对请求延迟与故障模式产生深远影响。

正如你无法在一个零犯罪率的祥和小镇里学会破案一样，你也无法在一个从不崩溃的玩具系统中学会诊断线上故障。简单的“Hello World”式 Demo 根本缺乏生产环境中所固有的长尾延迟、并发争用与局部故障。为了弥补这一鸿沟，本章引入了特意设计为复杂且充满挑战的微服务系统——**OpenTel E-Commerce**。

我们构建这个应用并不是为了图省事，而是为了追求极致的真实。它构成了我们在全书中注入混沌演练的基准线，是一个专门模拟分布式服务如何逐渐产生分歧并各自独立发生故障的实验沙箱。通过在一个库存预留会超时、数据库查询在负载下会退化、错误会层层级联雪崩的真实系统中摸爬滚打，我们为全面应用本书所讲授的 OpenTelemetry 体系搭建了理想的实战舞台。

这是一篇关于系统架构基准线的章节，而非遥测代码的具体实现篇。我们在此的目标是建立统一的系统上下文认知，以便从第 4 章开始，能够水到渠成地对这一整条端到端的请求旅程展开深度插桩与全景剖析。

## OpenTel E-Commerce：系统总体架构

OpenTel E-Commerce 遵循标准的微服务架构，注重职责的现实拆分而非教学式的简化。

![](/media/posts/rust-observability/img-06179.png)

*图 3.1 – OpenTel E-Commerce 架构：包含网关、三大后端微服务以及 Schema 逻辑隔离的 PostgreSQL 实例*

整个后端基于 Rust 语言与 Axum Web 框架构建，围绕一个中心 API 网关与三个核心微服务展开。系统依赖 HTTP REST API 进行跨服务通信，完美复刻了现代生产环境中的网络隔离特性。该架构在依托 Rust 类型系统实现极致性能的同时，完整保留了分布式协同的复杂性，打造了一个“单体内部严谨健壮、跨服务全局充满挑战”的真实环境：

- **OtelMart Service（API 网关）**：作为整个系统的统一入口，实现了 **BFF（Backend-for-Frontend）** 模式。BFF 不会向客户端直接暴露底层原始的后端接口，而是专门针对前端视图的需要，对数据进行聚合、过滤与整形。它通过 HTTP 代理将商品目录浏览与结账流量分发至对应的后端微服务。
- **Products Service（商品服务）**：管理整个电商商品目录。鉴于其极度读多写少的业务特性，需要原生支持复杂的搜索与分类检索逻辑。
- **Inventory Service（库存服务）**：作为商品真实库存的唯一事实来源（Source of Truth）。负责处理高并发的写入操作（库存锁定与扣减预留），并确保强一致性。
- **Orders Service（订单服务）**：充当分布式业务编排器（Orchestrator），掌控结账生命周期的流转，负责跨商品、库存与支付环节协同数据。

所有微服务统一使用同一个 PostgreSQL 物理数据库实例，但通过**独立的 Schema** 进行逻辑隔离——分别为 products、inventory、orders 和 users 维护各自专属的命名空间。我们之所以选用单物理数据库，纯粹是为了减轻读者在本地运行 Docker 时的资源开销；从 Rust 服务内部与 OpenTelemetry 观测链路的角度来看，查询不同 Schema 所产生的分布式追踪复杂度，与查询多台物理隔离的数据库完全一致。每个微服务均作为独立的容器化进程运行，各服务之间**绝不共享数据库连接**，彼此之间仅通过 HTTP REST API 进行网络通信。

我们是如何防止各服务越权访问其他服务的表的呢？每个服务在初始化数据库连接池时都会显式指定搜索路径。例如，Inventory 服务将其连接池配置为 `search_path TO inventory`，这样类似 `SELECT * FROM product_inventory` 的 SQL 查询就会自动解析为 `inventory.product_inventory`，而无需在业务代码中显式添加 Schema 前缀。其他每个服务也以同样的方式配置属于自己的专属 Schema。

需要明确的是，这是一种**工程规范，而非强硬的安全隔离边界**；某一个服务如果写出诸如 `orders.orders` 这样的全限定表名，在当前权限下依然*能够*直接读取。在严苛的生产环境中，你应当通过配置 PostgreSQL 角色权限来强制推行硬隔离。但在我们的实战场景中，这项规范已经完全足够：它确保了各个服务自觉各行其道，如果 Orders 服务需要获取商品数据，它就必须老老实实通过 HTTP 跨网络调用 Products 服务的 API。正是这种典型的跨服务通信模式，让分布式追踪变得不可或缺。

**本地运行方式**：我们使用 Docker Compose 统一编排所有服务。每个服务在各自独立的容器中运行，并对应隔离的数据库 Schema。服务之间通过 Docker 内部虚拟网络利用容器主机名（例如 `http://orders:3003`）互相发现并通信。当你运行 `docker-compose up --build` 时，你启动的绝非仅仅是几个容器，而是拉起了一整套伴随着网络分区、服务启动时序竞争、局部容灾与数据隔离等各种复杂故障模式的真实分布式系统。关于环境初始化的详细步骤，请参见仓库根目录下的 README。

## 领域建模：从数据库到 Rust 类型

理解了服务边界之后，我们来看看数据如何在它们之间流转。摆在我们面前的第一个核心挑战是：**实体身份标识（Identity）**。

一个设计精良的领域模型能够严丝合缝地连接起数据库 Schema 与业务代码。在 OpenTel E-Commerce 中，我们必须在金融交易所要求的绝对正确性与现代电商商品检索所需的敏捷灵活性之间取得完美平衡。

### 标识符策略与强类型设计

在分布式系统中，首要面对的挑战之一就是实体 ID 的设计。我们采用了**双主键标识符策略（Dual Identifier Strategy）**：

- **内部数字 ID (`i32`)**：严格仅用于数据库单表内部的主键自增、关联查询与外键索引，保证极佳的索引读写性能。然而，这种纯自增数字在跨数据库或跨微服务时极易发生碰撞冲突。
- **外部业务 ID (`UUID`)**：作为暴露给前端及其他微服务的唯一全局凭证。它不仅能够彻底杜绝遍历爬取攻击（Enumeration Attacks），还允许客户端或上游服务在无需向数据库发起往返请求的前提下，在本地离线生成 ID。与数字自增 ID 不同，UUID 保证在全局所有微服务与所有数据库集群中拥有绝对的全局唯一性。

在 Rust 代码中，这种双重映射关系具体表现如下：

```rust
#[derive(Debug, Clone, Serialize, Deserialize, FromRow)]
pub struct Product {
    pub id: i32,
    pub uuid: Uuid,
    // ...
}
```

`id` 字段声明为公开字段，以便 SQLx 的 `FromRow` 派生宏能够直接从数据库查询结果集填充数据。为了防止内部自增 ID 意外泄露到对外暴露的 HTTP 响应体中，我们面向客户端的数据传输结构体（如 `ProductDetail`）在 `id` 字段上标记了 `#[serde(skip)]`，从而对客户端保持透明，同时又不影响数据库访问层的直接使用。我们在此直接使用原生的 `i32` 而非引入 `ProductId(i32)` 这样的 Newtype 强类型包裹，旨在让初始代码基线尽可能直观简洁。由于内部 ID 绝不会跨越服务边界传播（跨网络通信一律只传递 UUID），在工程实践中不同服务间混淆内部 ID 的概率极低。

这种基于 UUID 的设计对于分布式系统至关重要。当 Orders 服务需要获取商品详情时，它会将商品的 UUID 传递给 Products 服务。这确保了即便各个微服务底层使用的是完全独立的异构数据库，同一个业务实体在全链路中始终携带全局统一的标识符。这极大简化了分布式排障：你可以在所有服务的海量日志与追踪中针对特定业务实体进行全局检索（例如“列出与该特定商品相关的所有追踪”）。
然而，必须将**实体标识**与**请求追踪**严格区分开来：同一个商品 UUID 可能会同时出现在数以千计的并发请求中；而后续章节引入的 Trace ID，则是为每一次独立的业务操作流赋予全局唯一的链路标识，从而把整趟跨服务的流转旅程严密串联在一起。

此外，我们在处理所有涉及金钱的数值时，**坚决杜绝使用浮点数**。尽管 `f64` 在图形计算中游刃有余，但在金融定价场景中，其舍入误差是绝对不可接受的。我们采用 `bigdecimal::BigDecimal`（对应映射到 PostgreSQL 的 `DECIMAL` 类型），确保“10.00 美元”在底层物理存储与计算中永远精确等于“10.00 美元”。这对于可观测性同样意义重大：当你将成交总金额作为监控指标上报，或者将购物车结算金额挂载为追踪属性时，你必须保证遥测数据与数据库记录毫厘不差，彻底规避类似 `$10.00000001` 这种可能导致财务看板对账失败的浮点漂移。

## 服务边界与核心职责

### OtelMart Gateway（BFF 网关）

作为所有客户端流量的唯一入口，网关充当了面向 Products、Inventory 和 Orders 服务的透明反向代理，负责将各微服务的原子响应聚合并整形为适合 Angular 前端消费的视图数据。在整本书中，网关承载着一个特意保持极简的核心业务流：**游客结账（Guest Checkout）**。客户的邮箱地址和收货信息直接随请求体一同传入，`orders.is_guest_order` 默认置为 `true`——整条追踪链路上没有复杂的身份鉴权逻辑。这种刻意为之的简化，是为了让读者在前期将全部注意力聚焦在分布式追踪的底层机制上，而不是陷入繁杂的认证授权管道中。

从可观测性的角度来看，网关是请求链路天然的根锚点。在第 4 章中，它将成为全链路追踪的起点：在此处创建根 Span（Root Span），并注入请求维度的全局属性（如客户邮箱），使下游的所有微服务都能够自动继承该全局上下文。

### Products Service（商品服务）

商品服务管理着层级化的分类目录，采用**物化路径模式（Materialized Path Pattern）**（例如路径格式形如 `1/23/45`），使得单次 SQL 查询即可高效检索出特定分类下的完整子树节点。商品信息充分利用 PostgreSQL 的 **GIN（广义倒排索引）** 索引，支持对商品名称和详细描述进行高性能的全文检索。与传统 B 树索引（一个键值严格映射到一行数据）不同，GIN 索引会将文本拆解为词元（Token），并将每个词元分别映射到包含它的所有行记录，是处理文本模糊检索的利器。这使得我们在主业务数据库内部就直接具备了接近专业搜索引擎的检索能力。

### Inventory Service（库存服务）

库存服务肩负着整个系统最神圣的一项使命：**绝不超卖**。除此以外，一切皆可商量。在数据库设计中，`available_quantity`（可用库存）并非一个由应用程序手动维护更新的普通列，而是 PostgreSQL 的**生成列（Generated Column）**，计算公式为 `stock_quantity - reserved_quantity`。生成列是数据库层面的计算字段：每当物理库存 `stock_quantity` 或锁定库存 `reserved_quantity` 发生变动时，PostgreSQL 会在底层**自动**重新计算出最新的可用库存。这在数学层面严丝合缝地保证了可用库存与实际物理库存及锁定库存之间的恒等约束——这种一致性由数据库内核亲自捍卫，而非脆弱的应用层代码。我们绝不会因为应用层的一条有缺陷的 SQL 或遗漏的代码分支而导致数据失真。

### Orders Service（订单服务）

订单服务集中体现了真实交易系统的终极复杂性。一个“订单”绝非数据库里一条简简单单的记录，它是买卖双方在特定时间点达成的一份具备法律与商业约束力的不可逆契约快照。

这里的设计决策揭示了将理论系统与严苛生产系统区分开来的核心架构原则：**通过数据非规范化换取不可变性（Denormalization for Immutability）**。当订单生成时，我们并不仅仅保存一个简单的 `product_id` 外部关联引用，而是将当时的 `product_name`、`sku` 和 `unit_price`（成交单价）**硬拷贝**直接固化持久化到 `order_items` 表中。乍看之下，这种冗余似乎是在浪费存储空间。为什么要冗余拷贝这些数据？

试想在真实的零售场景中，商品价格随时都可能发生调整。一个月后，用户登录系统查看历史订单。如果我们当初只记录了 `product_id`，系统就只能从当前的最新商品库中动态读取价格。用户赫然发现自己当初按 29.99 美元购买的商品，订单明细里显示的却是现价 19.99 美元。当愤怒的用户致电客服质问“为什么扣了我 30 美元，但订单上写着 20 美元？”时，你不仅凭空制造了一起客服纠纷，更严重透支了用户的信任。

在工业级生产系统中，这种非规范化的历史快照在以下三方面是不容妥协的刚需：
- **可审计性与故障复原**：每个订单都是特定历史时间点的不可变状态快照。当排查与某次具体结账追踪相关的线上事故时，拥有快照意味着你无需绞尽脑汁去推测“当时那个时刻这件商品的配置究竟是什么”。
- **合规审计**：全球各地的财税制度、消费者权益保护法以及信用卡拒付仲裁，均强制要求保留交易发生时的不可篡改原始凭证。
- **客户服务**：当出现扣款争议时，你必须确切掌握用户当时买的是什么、单价是多少；绝不能依赖后续已经被多次修改的动态数据表去反推历史。

从可观测性的角度来看，这些设计决策——用于跨链路关联的稳定全局 UUID、以及用于保障遥测数据稳定的非规范化快照——将变动不居、混乱混沌的底层数据库，塑造成了支撑分布式追踪的可靠基石。在一次 P1 级重大生产事故中为了还原现场而焦头烂额、或是面对监管合规调查时疲于自证的运维成本，远远超过了多冗余存储几个字段所付出的微小代价。

## 代码仓库导航

在深入探讨分布式事务之前，我们先梳理一下代码仓库的物理组织结构。该项目采用统一的 Cargo Workspace 进行单仓管理，包含四个核心成员 Crate：

```
opentel-ecommerce/
├── otelmart/             # OtelMart 网关服务（端口 4200）
├── products/             # Products 商品服务（端口 3001）
├── inventory/            # Inventory 库存服务（端口 3002）
├── orders/               # Orders 订单服务（端口 3003）
├── schemas/
│   └── init/             # 各服务专属的 SQL 初始化 Schema 脚本
├── Cargo.toml            # Workspace 根配置文件
└── docker-compose.yml    # 本地容器化编排文件
```

*图 3.2 – OpenTel E-Commerce 仓库的 Cargo Workspace 目录拓扑*

每个独立的微服务工程都遵循统一规范的内部目录结构：

```
orders/
├── src/
│   ├── handlers/         # HTTP 端点业务处理器（create_order, get_order 等）
│   ├── models/           # 领域实体模型（Order, OrderItem, OrderStatus 等）
│   ├── db/               # 数据库底层交互与仓储层实现
│   └── main.rs           # 服务启动入口、路由绑定与中间件配置
├── Cargo.toml            # 依赖声明（axum, sqlx, tokio 等）
└── Dockerfile            # 容器镜像构建文件
```

*图 3.3 – 微服务 Crate 的内部标准目录结构（以 Orders 服务为例）*

**重点研读文件索引：**
- `orders/src/handlers/orders.rs`：`create_order` 核心处理器，在此处编排驱动 Saga 分布式事务。
- `inventory/src/handlers/inventory.rs`：处理库存预留锁定与确认扣减的端点逻辑。
- `products/src/db/mod.rs`：包含支持全文检索的商品目录底层 SQL 查询。
- `schemas/init/`：各微服务专属的独立数据库表结构与索引定义文件。

在后续章节中阅读代码时，你将亲眼见证这些业务处理器是如何一步步被 OpenTelemetry 全面武装起来的。但在当前阶段，它们仅仅是纯粹的原生 Rust 函数，发起简单的 HTTP 网络调用与 SQL 交互——这正是最急需可观测性介入的典型代码。

## 跨服务通信机制：分布式事务

这些微服务并非孤立生存。当用户点击“购买”时，三大微服务必须协同作战——且任何一个环节都可能随时崩溃。我们来看看系统是如何应对这种复杂性的。

微服务之间必须通过高效的通信来达成复杂的商业目标。在 OpenTel E-Commerce 中，最核心的业务主链路莫过于**创建订单**。这一动作绝不仅是一次简单的数据库 `INSERT`，而是一场跨越三大独立微服务和多个不同故障域的典型分布式事务。

### 正常业务路径（Happy Path）

当用户点击购买时，**Orders Service** 充当分布式协调者的角色：
1. **校验（Validate）**：向上游 **Products Service** 请求商品最新详情（价格、名称），确保用户没有购买已下架或篡改价格的商品。
2. **预留（Reserve）**：向下游 **Inventory Service** 发出锁库指令：“为商品 X 预留锁定 1 件库存”。
3. **持久化（Commit）**：**唯有**在库存预留成功之后，订单服务才在自己的数据库事务中正式落盘订单记录。
4. **确认（Confirm）**：订单落盘成功后，最后向库存服务发送确认指令，将此前临时锁定的库存永久转为真实扣减。

### 异常回滚路径（Unhappy Path）

在传统的单体架构中，这整个调用序列完全可以包裹在单个物理数据库事务（`BEGIN...COMMIT`）中。如果任何一步发生异常，数据库内核会自动执行原子回滚。

然而在分布式微服务架构中，**物理上的全局事务回滚根本不复存在**。

如果订单服务成功预留了库存，但在后续落盘保存订单时发生失败（例如数据库磁盘被写满、或者代码逻辑发生异常 Panic），系统就会产生**孤儿库存锁定（Orphaned Stock Reservation）**：库存服务以为这件商品已经被买走了，但订单库里却查无此单。

为了解决这一难题，我们引入了 **Saga 模式**。Saga 是一种管理分布式长事务的核心设计范式：它不再强求底层的单一物理事务回滚，而是要求每个参与的服务在遇到失败时，通过显式调用下游服务的**补偿操作（Compensating Operation）**来抵消之前已完成的影响。当某一阶段发生故障时，系统手动发起逆向补偿请求以撤销之前的中间状态。以下是 `create_order` 处理器中的核心关键逻辑：

```rust
// 1. 尝试锁定预留库存
match reserve_stock(&state, item.product_uuid, item.quantity).await {
    Ok(_) => {
        reserved_items.push((item.product_uuid, item.quantity));
    }
    Err(response) => {
        // 如果当前商品库存锁定失败，我们必须手动释放【在此之前】已经成功锁定的所有其他商品。
        // 这是一种尽力而为（Best-effort）的逆向补偿：即使释放调用本身失败了，我们也只能记录日志并继续。
        // 在生产环境中，通常需要依靠后台对账任务（Reconciliation Job）来兜底捕获泄漏的锁定。
        release_all_reserved_stock(&state, &reserved_items).await;
        return response; // 直接返回错误 HTTP 响应
    }
}

// ...

// 2. 尝试向订单库提交事务落盘
if let Err(e) = tx.commit().await {
    // 极其严重的关键异常：本地订单数据库提交失败，但我们之前已经成功在库存服务中锁定了库存！
    // 我们必须手动跨网络调用库存服务的 API，反向撤销释放先前的库存锁定。
    release_all_reserved_stock(&state, &reserved_items).await;
    return (
        StatusCode::INTERNAL_SERVER_ERROR,
        Json(serde_json::json!({
            "error": "Failed to commit transaction",
            "details": e.to_string()
        })),
    )
        .into_response();
}
```

> **说明**
>
> 为保证行文清晰，上述代码段做了一定程度的精简。完整的处理器实现可参见仓库中的 `orders/src/handlers/orders.rs`，其中还包含商品合法性校验、支付记录创建以及落盘成功后的 `confirm_all_sales` 永久扣减逻辑。

请注意：代码在调用 `release_all_reserved_stock` 时，甚至无法强制阻断并捕获其返回值。这是典型的**尽力而为型补偿（Best-Effort Compensation）**。该函数会在内部记录错误日志，但如果连回滚补偿网络调用本身都超时失败了，业务线程没有任何手段能够立刻完成自愈。
这个 `release_all_reserved_stock` 函数是通过网络 HTTP 调用下游的 Inventory 服务的。**但如果此时网络恰好断开连接呢？**

如果网络发生分区中断导致解锁失败，系统将彻底堕入数据不一致的深渊。我们实质上“泄漏”了物理库存——商品在库存系统中被死死冻结为已预留，但在订单系统中却没有任何有效订单与其对应。在终端客户眼中，结账报错失败了，于是他会刷新页面重试；但库存服务依然保留着上一次锁定的记录，直接导致可用库存不足并报错超卖。这是分布式架构中极其经典的顽疾，也是客服工单中真正的噩梦：“幽灵锁定”、库存账实不符、营业额无端流失。**在缺乏可观测性的前提下，你根本没有任何手段能够主动捕获并定位这种隐蔽的静默泄漏。**

这正是分布式追踪在治理 Saga 模式时展现无可替代价值的地方。在理想状态下，整个 `create_order` 流程会被捕获为一个顶层根追踪；Saga 链路中的每一个原子步骤——预留库存、落盘数据库，尤其是**执行补偿动作**（如 `release_all_reserved_stock`）——都会作为子 Span 紧密挂载在主链路上。一旦事务发生异常，生成的追踪瀑布图绝不仅仅是干瘪地标红报错，而是**用时间线完整还原整场故障自愈与补偿的执行过程**。你能清晰看到系统发起了哪些补偿动作、耗时多少、补偿请求是成功抵达了对端还是中途遭遇了网络中断，从而将一场错综复杂的跨服务灾难转化为了脉络清晰、按时间演进的直观故事。

## 后端请求全链路流转

为了明确后续章节中我们需要插桩的具体目标，我们先沿着一个标准的结账请求，追踪它从最外层 HTTP 入口一直深入到数据库持久化的完整生命周期。这也是本书后续用来贯穿展示各项可观测性范式的**基准请求链路（Canonical Request Flow）**。

### 标准结账请求全景链路（HTTP 入口到数据库）

当终端用户在 Web 前端点击“立即购买”时，其背后经历的完整旅程如下：

1. **HTTP 入口 -> OtelMart Gateway（端口 4200）**
   - **操作步骤**：`POST /api/orders`
   - **具体行为**：接收结账请求 Payload，包含目标商品 UUID、选购数量、收货地址与支付明细
   - **核心职责**：执行统一路由转发（本场景为游客结账，暂不校验 Session）
2. **Gateway -> Orders Service（端口 3003）**
   - **操作步骤**：`POST http://orders:3003/orders`（反向代理分发）
   - **具体行为**：将结账报文精准投递给 Orders 编排服务
   - **技术要点**：分布式追踪上下文将通过标准 HTTP 请求头在此处跨进程注入与传递（详见第 4 章）
3. **Orders -> Products Service（端口 3001）**
   - **操作步骤**：`GET http://products:3001/products/{uuid}`
   - **具体行为**：查询商品实时元数据（核对单价、名称与上下架状态）
   - **数据库操作**：Products 服务内部执行 `SELECT` 查询 `products.products` 表
   - **业务动因**：Orders 必须基于不可篡改的后端真实价格重新计费
4. **Orders -> Inventory Service（端口 3002）**
   - **操作步骤**：`POST http://inventory:3002/inventory/reserve`
   - **具体行为**：为当前订单临时锁定并预留库存
   - **数据库操作**：Inventory 服务执行 `UPDATE` 更新 `inventory.product_inventory` 表
   - **业务动因**：杜绝并发超卖（Saga 模式第一阶段）
5. **Orders -> 订单服务自身数据库**
   - **操作步骤**：`INSERT INTO orders.orders`
   - **具体行为**：将订单与明细原子写入订单数据库
   - **数据库操作**：对 `orders.orders` 与 `orders.order_items` 表执行持久化插入
   - **业务动因**：生成具备不可变历史快照意义的订单记录
6. **Orders -> Inventory Service（端口 3002）**
   - **操作步骤**：`POST http://inventory:3002/inventory/confirm-sale`
   - **具体行为**：确认库存划扣（Saga 模式第二阶段）
   - **数据库操作**：Inventory 服务将先前锁定的库存最终结算为已售出扣减
   - **业务动因**：彻底完成该笔分布式事务闭环
7. **响应级联返回**
   - 响应由 Orders -> 返回至 Gateway -> 最终回传至前端用户 Client
   - 各级微服务依次沿调用栈向上传递处理结果或错误信息

### 跨微服务调用的全景拓扑映射

这仅仅一次看似普通的结账动作，在幕后触碰了：
- **4 个独立微服务**（Gateway、Orders、Products、Inventory）
- **3 个独立逻辑 Schema**（`products`、`inventory`、`orders`）
- **6 次跨网络 HTTP 调用跳步**
- **4 次深度的物理数据库 SQL 交互**（SELECT products、UPDATE inventory、INSERT orders、UPDATE inventory）

**在缺乏分布式追踪的世界里**，排查一次结账缓慢简直是无休止的折磨：
1. 登录 Gateway 查看网关日志
2. 人肉寻找关联标识（如果你此前有意识打印了的话）
3. 拿着标识去翻找 Orders 服务的日志
4. 再去翻找 Products 服务的日志
5. 再去翻找 Inventory 服务的日志
6. 借助各机器上可能存在毫秒级时钟漂移的时间戳，人肉拼凑时间线
7. 靠直觉胡乱猜测究竟是哪一次网络调用或 SQL 查询拖慢了系统

**而在拥有分布式追踪的世界里**，整条链路在统一看板中尽收眼底：
- 直观的可视化瀑布图，每一步耗时一目了然
- 全链路所有跨进程微服务的自动化因果关联
- 每一条 SQL 查询语句的真实物理耗时被精准高亮
- 跨服务之间的网络传输与排队开销清澈透明

到本书第二部分结束时，这条基准链路将彻底脱胎换骨，实现百分之百的深度可观测——每一次跳步均被追踪，每一条查询均被度量，每一个错误都携带完整的上下文字段。

## 系统现状：缺乏可观测性的原始日志

在当前基线代码中，我们试图用最原始的 `println!` 来抵御这场复杂的混沌：

```rust
println!("正在为用户创建订单: {}", request.customer_email);
// ...
eprintln!("获取商品详情失败 {}: {}", product_uuid, e);
```

当一切风平浪静时，这似乎勉强能跑；可一旦在线上遭遇并发故障，这就是一场灾难。

### 令人窒息的“黑盒困境”

设想一次订单创建在线上挂掉了。你在 Orders 服务的日志里看到孤零零的一行报错：
`[ERROR] Failed to reserve stock for product a7f3c5...`

但**原因**究竟是什么？是 Inventory 服务宕机了？还是响应太慢超时了？对端返回的是 400 业务拒绝还是 500 内部崩溃？
为了找到答案，你必须切出终端，执行 `docker logs` 查看 Inventory 服务容器的输出，猜测当时的大致时间窗口（祈祷各容器没有时钟漂移），并在茫茫日志中 grep 这个商品 UUID。

如果一个请求穿透了 5 个微服务，你就必须在 5 台服务器上反复 grep 5 份孤立的日志文件。

### 结构化日志：仅仅迈出了半步

我们可以借助 `tracing` crate 引入**结构化日志**来改善这一现状。不再打印无序的纯文本，而是输出结构化的 JSON 字段：

```rust
info!(
    customer_email = %request.customer_email,
    item_count = request.items.len(),
    "收到创建订单请求"
);
```

这确实让我们具备了基于字段检索日志的能力（例如过滤 `item_count > 5`），但它依然**完全缺乏因果关系（Causality）**。它无法证明 Inventory 服务里的*这条*报错日志，究竟是由 Orders 服务发起的*哪一个*具体请求所引发的。

为了缝合这个断层，业内通常的做法是引入 **Correlation ID（关联 ID）**——在服务间通信时通过自定义 HTTP 请求头（如 `X-Correlation-ID`）沿途传递唯一字符串。

**网关侧**负责生成并向前传递：

```rust
// 网关为每个进入的请求生成唯一的 Correlation ID
let correlation_id = Uuid::new_v4();

// 将其注入请求头向下游 Orders 服务转发
let orders_response = state.http_client()
    .post(&orders_url)
    .header("X-Correlation-ID", correlation_id.to_string())
    .send()
    .await?;
```

**订单服务侧**负责解析并继续传播：

```rust
// 订单服务从上游请求头中提取 Correlation ID
let correlation_id = headers
    .get("X-Correlation-ID")
    .expect("网关必须传递 X-Correlation-ID");

// 并继续注入请求头透传给下游 Inventory 服务
let inventory_response = state.http_client()
    .post(&inventory_url)
    .header("X-Correlation-ID", correlation_id.to_string())
    .send()
    .await?;
```

引入 Correlation ID 之后，单个业务请求终于能够跨越微服务被串联在一起了。当你拿着一个特定的 Correlation ID 去日志系统搜索时，网关、订单和库存服务的相关日志行会同时呈现出来——把整条零散的请求流重新拼装成一个整体。这是迈向可观测性的坚实第一步。

> **说明**
>
> OpenTelemetry 并没有抛弃 Correlation ID 的思想；相反，它将这种机制进行了严格的工业级标准化与全自动化。你无需在业务代码中到处手动硬编码传递自定义的 `X-Correlation-ID` 请求头，OpenTelemetry 会自动基于 W3C Trace Context 国际规范标准（例如 `traceparent` 头）在底层完成透明的上下文传播。

然而，即便拥有了 Correlation ID，我们依然缺失了一个最致命的维度——**时间流逝维度（Time Dimension）**。
我们虽然知道了系统里究竟*发生*了什么，却依然无法回答**时间究竟消耗在了哪里**。哪个服务最慢？延迟究竟是发生在网络传输中，还是发生在数据库执行上？日志忠实记录了离散的*事件*，却无法直观勾勒出*耗时*。

## 为什么可观测性是刚需而非可选项

在 OpenTel 电商系统中，一次迟缓的结账请求可能是由下列任何一个环节引发的：
1. Orders 服务中执行了低效的慢 SQL。
2. Orders 与 Products 微服务之间的跨网络传输发生丢包或阻塞。
3. Inventory 服务的数据库遭遇了严重的行级排它锁争用。
4. Gateway 网关的异步执行器中有同步阻塞代码卡死了工作线程。

日志——即便经过精心设计的结构化 JSON 日志——在本质上都只是时间轴上零散分布的**离散孤岛**。它们只能告诉你特定时刻发生了某件事，却无法展示两件事之间那段漫长的空白时间里到底在发生什么。它们无法展现那些**隐蔽的时间断层**。有了 Correlation ID，你仅仅知道这个请求路过了哪些服务，却根本不知道是谁在拖后腿。

这正是我们必须引入**分布式追踪（Distributed Tracing）**的根本动因。分布式追踪将离散的日志点熔炼成一条连续的时间轴。它不再只记录冰冷的事件点，而是记录一段段带有始末的**耗时跨度（Durations）**：请求在每个微服务上停留了多久？跨网络网络调用耗费了多少微秒？追踪将复杂的请求流向绘制为直观的可视化图表，自动将延迟瓶颈暴露在聚光灯下。你会一眼洞穿：那长达 2 秒的停顿究竟发生在向库存服务发起网络调用的**传输中**，还是发生在订单数据的插入落盘时；你会立刻发现 Inventory 仅仅为了等待一行数据的行锁就耗费了整整 1.8 秒，而上游的 Products 检索仅仅花费了微不足道的 0.1 秒。

## 本章小结

至此，我们已经完整确立了后续演练的基准战场：
- **逼真的微服务拓扑**：边界分明、各司其职的独立微服务体系。
- **直面生产级复杂性**：网络延迟、局部故障、分布式事务与 Saga 补偿机制。
- **显而易见的可观测性断层**：空有原始日志，却无法在全局建立对系统行为的宏观洞察。

所有的“混乱土壤”已全部就绪。现在，我们急需专业的工程武器来征服它。传统的关联 ID 虽能串联日志，但在每个边界都需要大量手写硬编码；传统的结构化日志虽能检索，却对耗时与因果关系的度量束手无策。

在接下来的**第 4 章**中，OpenTelemetry 将终结这种笨拙的手动传参和秒表计时。它将以非侵入且标准化的方式对我们的 Rust 业务代码进行深度插桩，无需改动任何业务领域逻辑，即可全自动捕获完整的请求拓扑链路——谁调用了谁、每一步耗时多久、故障在何处引爆，全景全貌，纤毫毕现。
