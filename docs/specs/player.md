# 播放器功能规格（player）

> 状态：已确认（2026-09-14）
> 上位：`docs/specs/ui-ux.md` §5（完整小播放器）。本文定行为与边界，不定技术实现。
> 与代码的关系：本文是判定标准；现有实现与本文不一致处见 §9 缺口清单，按缺口顺序实现。

## 1. 队列模型

1. 播放器持有**一份**队列：有序曲目表 + 当前位置 + 播放/暂停态。全站唯一，任何页面共享。
2. 入队即起播：`播放专辑（曲目表，起始位置 = 首首）` 把队列设为给定曲目并从起始位置播放；起始位置可指定（专辑详情从任一单曲起播）。
3. 曲目顺序 = 专辑曲目顺序 = 入队顺序；「播放全部」从第一首起播。
4. 同一份专辑的识别按**内容**（曲目标识序列一致即同一份），不按对象引用——跨页面入队后状态判断不得失效。
5. 空曲目表入队直接忽略，状态纹丝不动。

## 2. 播放 / 暂停

1. 暂停只停声音，不动队列、不动位置、不丢进度；恢复从暂停处继续，**不得**从头重播。
2. 切换曲目时才换音频源；同曲目内的暂停/恢复/重复点击绝不重载音频（进度归零是 bug）。
3. 正在播的专辑，其专辑卡按钮与「播放全部」按钮呈"暂停"态，再点即暂停而非重播；暂停态下再点即恢复。

## 3. 上一首 / 下一首

1. 下一首：当前位置非末首时前进一步并起播；已在末首时停留不动（不循环、不报错）。
2. 上一首：当前位置非首首时后退一步并起播；已在首首时停留不动。
3. 切歌后按当前播放态恢复：播放中切歌继续播，暂停中切歌保持暂停（只换位置，不偷播）。

## 4. 自然结束

1. 一首播完自动进下一首（播放态延续）。
2. 末首播完停止：回到暂停态，位置停在末首，队列保留（用户可重播或切歌）。

## 5. 进度与时间（§5 必备能力）

1. 播放条必备：上一首 / 播放·暂停 / 下一首 / 进度（可拖拽、可键盘调节）/ 当前时间与总时长 / 关闭，缺一不可。
2. 进度诚实三位一体：自然播放推进、拖拽跳转、键盘调节，三者指向同一位置，互相不打架（拖拽中自然推进不抢夺手柄）。
3. 时间如实显示：当前时间与总时长文本可见；时长未知（如元数据缺失、流未加载）时如实表达未知态，不编造数字、不显示 `NaN`。
4. 拖拽超出边界时钳制到首尾，不抛错。

## 6. 音量控制

1. 音量范围 0–1，默认 1；静音是独立态——静音记住静音前音量，取消静音恢复（而非归零或拉满）。
2. 控件 = 静音按钮 + 音量滑杆：按钮一键静音/恢复，滑杆可拖拽、可键盘调节；图标随状态变化（有声/小声/静音，通用隐喻，沿用图标化规范）。
3. 拖到 0 即静音表现（图标切静音态）；从 0 拉起即取消静音，两者互通不打架。
4. 平台差异诚实处理：部分移动端浏览器忽略程序化音量（以系统音量键为准）——此时控件保持可用、不报错、不做平台分支界面；桌面端完整生效。
5. 音量与静音态持久化到本地（与主题偏好同理的纯客户端存储），异常时降级为本次会话生效；刷新不丢音量偏好（队列仍不持久化，见 §9.3）。
6. 窄屏精简时音量控件可收起，核心控制（播放·暂停/切歌/进度/关闭）永远可达。

## 7. 关闭语义

1. 关闭 = 停止声音 + 清空队列 + 位置复位 + 播放条消失（恢复零留白）。
2. 关闭后重新起播从新的入队开始，不恢复旧队列。

## 8. 自动播放与浏览器策略

1. 永不自动起播：页面加载、页面跳转、队列就绪都不自动出声；第一次声音必须源于用户手势。
2. 浏览器拦截播放（如自动播放策略）时降级为暂停态，不抛错、不卡死，用户再点可播。

## 9. 错误与边界

1. 音频加载/解码失败时：停止播放（暂停态），保留队列与位置，用户可重试；**不**静默跳过（跳过会让用户对"在播哪首"产生误判）。
2. 单曲专辑：上一首/下一首均为停留，进度与时间正常可用。
3. 刷新页面丢失队列可接受（纯静态站，不做持久化）；但站内导航（客户端路由切换）播放必须连续。
4. 无队列时播放条整体不存在（零常驻留白）；任何控制按钮不得在无队列时可点。

## 10. 状态可见（与界面原则的衔接）

1. 播放条始终显示当前曲名 + 艺术家（有封面显示封面，无封面显示兜底图形）。
2. 当前播放的专辑卡按钮呈暂停态；专辑详情当前行高亮并有明确指示。
3. 所有控制按钮的无障碍名与悬停提示一致，沿用图标化三判据（`ui-ux.md` §3.4）。

## 11. 不做什么（v1）

1. 不做随机 / 单曲循环 / 列表循环模式：播完即停（§4.2）。
2. 不做播放历史与队列持久化（localStorage/IndexedDB）——仅音量偏好持久化（§6.5）。
3. 不做后台播放保障之外的平台特殊处理：浏览器切后台的行为遵循平台默认。

## 12. 技术选型：自研扩展（结论）

**结论**：现有 `PlayerProvider` + 单例 `HTMLAudioElement` 向前扩展，不引入音频库。

| 候选 | 结论 |
|---|---|
| **自研扩展**（现有 Provider + shadcn Slider + 原生音频事件） | ✅ 采用。规格内全部能力都在 `HTMLAudioElement` 原生范围内（播放/暂停/音量/静音/跳转/时长/事件）；队列模型已有实现与测试网；进度与音量共用已 vendor 的 Slider，不手写 `role="slider"` 逻辑 |
| howler.js 等音频引擎 | ❌ 不用。它解决的是 Web Audio 特效/雪碧图/多格式降级/iOS 自动解锁——本规格一条都不需要（§8.1 永不自动起播）；为用不上的能力付体积与队列模型适配成本 |
| ElevenLabs audio-player（headless Provider + 自组 UI，最接近"你写 UI、它管功能"） | ❌ 不用。它要整体替换已验证的队列核心，而队列语义正是本规格最特殊的部分（内容比较 §1.4、播完即停 §4.2、暂停不重载 §2.2）——适配加验证成本 ≥ 自研；且其 CLI 安装与 shadcn CLI 同类风险，厂商设计系统走向不明 |
| react-use-audio-player（hook + Howler） | ❌ 不用。单曲导向（逐首 load），队列仍得自写——省不掉 Provider，只把 `<audio>` 换成 Howl，多一层重量换零层语义 |

实现要点（只定方向，不定代码）：

1. 事件驱动，不轮询：进度靠 `timeupdate`，时长靠 `loadedmetadata`（+ `durationchange` 兜底），失败靠 `error`（→ §9.1），收尾靠既有 `ended`。
2. 拖拽互斥：手柄拖拽中自然推进不抢夺（拖拽态标记，松手后以手柄位置为准），对应 §5.2。
3. 音量直通 `volume` / `muted`，与 §6 状态机一致；偏好读写 localStorage 与主题偏好同 pattern（try/catch 降级）。
4. 进度与音量共用 shadcn Slider（`ui-ux.md` §5.5、本文 §13 要求）；`bg-secondary` 等 token 已进主题（接入轮补齐）。
